## 1. What a user gets

Both live in **Settings → Security**, beside the two-step and two-person panels.

**Access review (C-35).** One row per person with access — the workspace creator first, then the
member list — with:

| Column | Where the value comes from |
|---|---|
| Person | the owner uid and the workspace member uids (the same `/members` and `/roles` routes Settings → Team uses), with an email when the app can see one |
| Role | `workspace.roles` (owner forced for the creator); anything unknown reads as Viewer, the read-only role |
| Last sign-in | the newest `USER_LOGIN` audit entry of that person |
| Two-step login | the workspace rule plus proof, or the reader's own account — explained below |
| Role last changed | the newest `ROLE_CHANGE` audit entry whose `details.targetUid` is that person, with `before → after` and who made the change |

CSV (`Export CSV`) and `Print` use the same rows, one code path (`src/lib/accessReview.ts`).
Owners and accountants see it; bookkeepers, viewers and the demo workspace are told why they do not,
and a refused reader never asks the server for the names. Read-only: there is no control that
changes a role or a person anywhere in it.

**Audit evidence pack (C-36).** Pick a period and download one ZIP:

| File | Contents |
|---|---|
| `README.txt` | what the pack is, the period, when it was generated, and every limit below |
| `audit-log.csv` | audit entries dated inside the period, newest first (when, action, person, email, entity, description) |
| `period-locks.csv` | the hard lock and soft close in force, an open partial unlock, and every close/reopen/unlock/sign-off recorded in the period |
| `approvals.csv` | invoice approvals and pay-run approvals decided or asked for in the period, with the amount each document already stores |
| `approval-rules.csv` | the invoice approval limit, the two-person rule and pay-run approval as they stand |
| `access-review.csv` | the access review above, row for row |

It downloads for a period with no records too (each file then holds only its header row), because a
quiet period is evidence as well. The ZIP is written by `src/lib/zips.ts`: stored entries, UTF-8
names, correct CRCs and central directory, no dependency added.

## 2. What the screen does **not** claim (the honest part)

- **Last sign-in** is the app's own record of someone entering the workspace in a browser session,
  not every authentication event of the account (those live with the sign-in service). The audit
  trail in the browser loads the **newest 500 entries**, so the column says "Not in the recent audit
  entries" rather than "never", and the screen says that sentence as well.
- **Two-step login for another person** cannot be read from this app: authenticator factors belong to
  the sign-in service, and the app may only read the signed-in person's own. So the column says one of:
  - the workspace requires two-step for everyone **and** the person has a sign-in recorded after that
    rule was turned on — the server and database refuse a password-only session of a member, so this
    is proof they passed it ("On — signed in since the workspace required it");
  - required, but no later sign-in is in the entries shown ("Required by the workspace — no later
    sign-in shown") — which proves nothing about their authenticator;
  - no workspace rule and it is the reader: their own real state (on / off / could not be read);
  - no workspace rule and it is someone else: "Only that person can see it".
- **The pack** restates documents' own amounts and adds nothing up. It is not an audit opinion, and
  it does not include entries older than the loaded 500 or authentication events from the sign-in
  service.

**Handoff, if AI #1 wants fact instead of proof:** a read-only
`GET /api/v1/workspaces/:workspaceId/security/access` returning each member's last sign-in and
two-step status (read from the sign-in service) would let the column state it directly. The reader is
one function (`accessReviewRows`) and the screen needs no redesign; nothing here blocks on it.
